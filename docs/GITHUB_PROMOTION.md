# GitHub promotion — how a READY candidate becomes a pull request (and never a merge to `main`)

Status: **SHADOW PR PROMOTION: PROVEN (FakePromotionProvider) · REAL SOCIETY GITHUB APP: NOT YET CONFIGURED**

## The trust domains

| Identity | Holds | May |
| --- | --- | --- |
| Society agents (model) | nothing | emit `REQUEST_PR_PROMOTION` / `REQUEST_MERGE_EVALUATION` / `REQUEST_STAGING_EVALUATION` |
| Promotion Controller (`society/promotion.py`, non-LLM) | a short-lived token **inside the provider only** | validate from the trusted base, publish `agentnet-auto/<candidate-id>`, open/update a DRAFT PR, observe CI/reviews/merge, compute eligibility |
| Humans | GitHub review/merge rights | approve, merge (AMBER/RED always; GREEN while auto-merge is off) |
| Engineering sessions (e.g. the session that wrote this) | their own GitHub identity | never reused as the Society identity |

`main` (`SOCIETY_GITHUB_BASE_BRANCH`) is refused as a publish target in the controller and in every provider;
no provider method can force-push; a remote branch with different history is a conflict that supersedes the
promotion instead of being overwritten.

## Lifecycle (durable: `code_promotions`, events `promotion.*`)

```
requested ─► validating ─► branch_ready ─► pr_open ─► ci_pending ─► ci_passed ─► awaiting_approval ─► merge_eligible ─► merged
                │                                        │              │                 (human merges; observed)
                ├─► blocked_external (no provider)       ├─► ci_failed  └─► superseded (base moved / head changed / branch conflict)
                └─► rejected (validation) / superseded (sha changed, base not ancestor)
```

Validation (`promotion.validate`) requires: candidate READY on the exact head; branch under `SOCIETY_BRANCH_PREFIX`;
base sha an ancestor of the trusted base; **trusted risk tier** from the real diff (NEVER → rejected); no
never-writable file; files/diff-lines within budget; QA PASS for the exact head; Security PASS for the exact head
when the tier is AMBER/RED or findings exist; no secret-pattern finding; independent reviewer for RED.

Merge eligibility (`compute_eligibility`) — all must hold: `risk_promotable`, `ci_passed`, `branch_up_to_date`,
`head_unchanged`, `qa_pass`, `security_pass`, `no_critical_findings`, `fitness_precheck` (experiment PASS),
`no_unresolved_review`, `change_budget`, `human_approval_satisfied`. `auto_merge_allowed` additionally needs
tier GREEN and `SOCIETY_AUTO_MERGE_ENABLED=true` (default false; refused with the GitHub provider in this phase).

States that wait on the outside world (`pr_open`, `ci_pending`, `awaiting_approval`, `merge_eligible`,
`blocked_external`) are re-polled at most once per `SOCIETY_PROMOTION_POLL_INTERVAL_SECONDS` (default 60);
internal steps advance immediately. Leases (`SOCIETY_PROMOTION_LEASE_SECONDS`) make a crashed step re-claimable;
`SOCIETY_PROMOTION_MAX_ATTEMPTS` bounds transient provider faults before `rejected`.

The PR body is generated by `pr_body_from_facts` from persisted rows (proposal, correlation, tier, files,
acceptance criteria, QA, Security, fitness, rollback criteria). The model cannot edit it.

## Providers

| `SOCIETY_PROMOTION_PROVIDER` | Behaviour |
| --- | --- |
| `disabled` (default) | every promotion becomes `blocked_external`; nothing is published; resumes when a provider appears |
| `fake` | in-memory GitHub double: deterministic branch/PR numbers, scripted CI, simulated approvals/merges, injectable faults (transient, conflict, refused) — the shadow proof |

## Recommended `main` ruleset (owner action)

At authoring `main` had **no ruleset and no branch protection** (`GET /rules/branches/main` → `[]`). Recommended:

1. Require a pull request before merging (1 approval; dismiss stale approvals; require conversation resolution).
2. Require status checks to pass: the six CI jobs (Lint, Dependency audit, Per-service isolated environments,
   Unit + PostgreSQL-backed + Society + migrations + compose topology, Fresh install, Images build + compose render);
   "Require branches to be up to date before merging" ON.
3. Block force pushes (ON), Restrict deletions (ON), Require linear history (optional; squash merges satisfy it).
4. Bypass list: empty (no Society App, no controller).

The controller enforces "never `main`, never force" in code regardless of repository settings.
