# Maintenance OS — research baseline (what is adopted, and what deliberately is not)

Date: 2026-09-27. Scope: the patterns ADR-0010 builds on. **Sources re-read in this build session:**
Railway Public API docs (`docs.railway.com/integrations/api/manage-deployments`, `.../manage-services`,
via the Railway documentation connector) and GitHub's "Create custom deployment protection rules"
page. The other entries below are from the maintainers' working knowledge of those projects' current
official documentation and are stated as such; where an API name matters at runtime the code
**discovers it** instead of trusting this page (Railway schema introspection).

| Source | Adopted | Deliberately not adopted |
|---|---|---|
| **Kubernetes controllers / operators** (desired vs. observed state, level-triggered reconciliation, idempotent reconcile, leases, status as the record) | The whole kernel shape: `desired_state.json` + trusted observations; the reconciler re-reads persisted state every cycle and asks "what next / already done?"; events are wake-up hints only; leases with `FOR UPDATE SKIP LOCKED`; fencing before writes. | No Kubernetes, no CRDs, no controller-runtime: AgentNet runs on Railway and Postgres already gives durable status and leases. |
| **Temporal** (durable workflows, activities with timeouts/retries, deterministic workflow code, idempotency) | Semantics implemented on the existing platform: durable case rows = workflow state; `repair_activities` = activity executions with idempotency keys, try counts, timeouts, retry policy and classified failures; crash replays converge (tests kill the process at every boundary). | Temporal itself. ADR-0010 D6/D7 show the required semantics hold on PostgreSQL + worker loops; adding a Temporal cluster would add an operational dependency (and a paid plan or self-hosting) without closing a gap. Revisit only if multi-hour activities with heartbeats or cross-service sagas appear. |
| **Google SRE** (toil, SLOs, error budgets, error-budget policy, blameless postmortems) | SLIs/SLOs per product surface with minimum samples; deterministic error-budget accounting; the budget gates change velocity (innovation freezes, P0/P1/security repairs and rollbacks continue); toil counted per kind; KPIs (MTTD, MTTR, auto-repair/rollback/escalation/false-positive rates); postmortem facts are deterministic and blameless, a model may only explain them; "fix the detector" recorded on every terminal case. | Multi-window burn-rate alerting (the product's traffic is too small for meaningful burn rates yet); the SLO targets are stage-appropriate, not enterprise defaults. |
| **GitHub rulesets / required status checks** | Unchanged and binding for the release controller: PR to `production`, required CI, strict/up-to-date, no force push, no bypass actors. The release App has no admin and no bypass. | Any bypass; any ruleset edit by automation. |
| **GitHub merge queue** (`merge_group` event) | — | Not adopted now: maintenance holds one production release in flight (partial unique index) and GREEN main merges are capped at one per day; a queue adds CI (`merge_group`) complexity without a concurrency problem to solve. Re-evaluate if autonomous main merges exceed the cap. |
| **GitHub deployment environments / custom deployment protection rules** | — | Not adopted. Re-read 2026-09-27: the feature is **public preview**, and it gates *GitHub Actions deployment jobs* (the App answers `POST /repos/{owner}/{repo}/actions/runs/{run_id}/deployment_protection_rule`). AgentNet production deploys through Railway's *Wait for CI*, not an Actions deployment job, so it would gate nothing real. The Release Controller's own verification + the production ruleset is the gate. |
| **Railway Public GraphQL API** | Exact-SHA deploy `serviceInstanceDeployV2(serviceId, environmentId, commitSha)` (unknown SHA → "Commit not found", no deployment); `deploymentRollback(id)` (only when `canRollback`); `deployments(input:{projectId, serviceId, environmentId})` with `meta` (commit) and `canRollback`; `deployment(id)` status (`BUILDING DEPLOYING SUCCESS FAILED CRASHED REMOVED SLEEPING SKIPPED WAITING QUEUED`). **The provider introspects the live schema before use and refuses if a mutation/argument is missing** (no stale names). Project tokens via `Project-Access-Token`. | Rolling back "to previous" without identifying it: the controller records known-good deployment ids and SHAs before every release and falls back to redeploying the known-good SHA when an image expired (Hobby retention is finite). |
| **Playwright** | Real-browser deep-tier journeys, pinned Playwright 1.56 / its Chromium build; reduced-motion + animation-free visual-test mode with fixture data; structural checks run in-page. | Pixel screenshot comparison on production (particles, live data and dynamic ids make it meaningless). Screenshot baselines are not stored yet; semantic assertions are the gate. |
| **axe-core** | Pinned 4.10.3, WCAG 2.0/2.1/2.2 A and AA tags, rule ids + node counts only. Plus AgentNet's own deterministic contrast/label/raw-value/banner/overflow checks so the gate does not depend on one engine. | Sending axe's HTML snippets anywhere (they contain page text). |
| **Lighthouse CI** | — | Not adopted in this phase: its value (lab performance scores) is noisy on shared CI runners and the product's real risk today is correctness, not milliseconds. Pragmatic budgets (document bytes, total bytes, request count, third-party origins) are measured by the same Playwright probe and a single run never opens an incident (confirmation needs repeated observations). |
| **OpenTelemetry semantic conventions** | Structured, bounded names: `service`, `http.route`-style contract item names (never raw URLs — X1 stays closed), deployment ids, `maintenance.case.state`, release status; the existing OTLP exporter is unchanged. | New span instrumentation of the kernel (not needed for correctness; the durable transition log is the trace of record). Listed as a follow-up. |
| **OPA / Rego** | The *separation* is adopted: policy decides (`policy.py`, `slo.py`, `state_machine.py`), enforcement happens at the action (kernel, promotion freeze, release controller). | OPA itself: the existing deterministic Python policy expresses every rule, is imported from the running (trusted) revision, and is tested; a second policy runtime adds operational surface without a concrete benefit. |
| **Hypothesis** | Property-based tests of the state machine (random action/actor sequences). | — |
